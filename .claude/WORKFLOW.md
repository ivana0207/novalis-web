# Jira-driven multi-agent workflow - usage guide

You manage **what** gets built in Jira. Claude Code (the orchestrator) reads the tickets, plans, delegates to
specialist agents, tests, fixes and re-tests, and stops at **Ready for Human Review**. Nothing is pushed,
merged, deployed, published or written to Jira unless you ask for that specific action.

```
Jira ticket ──read only──▶ Requirements analyst ──▶ spec.md (ACs) ──▶ your confirmation if ACs were proposed
                                                         │
                         plan.md (only the agents the ticket needs)
                                                         ▼
          Designer · Content ──▶ Developer ──▶ QA · Visual/A11y · SEO · Code/Security (independent, parallel)
                                     ▲                 │ defects
                                     └──── fix loop ◀──┘ (budgeted; re-verified by the agent that found it)
                                                         ▼
                                   Delivery verifier ──▶ handoff.md + qa-report.md ──▶ you review locally
```

## Everyday commands (type them in Claude Code, in this project)

| You want to… | Say |
|---|---|
| Work on one ticket | `/jira-work WEB-25` or "Work on WEB-25" |
| Work on several | `/jira-work WEB-25 WEB-16 WEB-18` or "Work on WEB-25, WEB-16 and WEB-18" |
| Work on your open tickets | `/jira-work mine` or "Work on all my assigned tickets" (WEB has no sprints, so this uses "assigned to me, not done, not on hold"; it shows the list and how it groups related tickets, then works through them) |
| See the plan before anything is built | `/jira-work WEB-25 --plan-only` |
| Try the pipeline without building | `/jira-work WEB-25 --dry-run` |
| Resume after closing Claude Code | `/jira-work continue WEB-25` or "Continue the unfinished local work for WEB-25" |
| Check progress | `/jira-work status` or "Show me the progress of my current tickets" |
| Get the final review package | `/jira-work review WEB-25` or "Prepare WEB-25 for my final review" |

It asks you only for business decisions: proposed acceptance criteria, design-direction changes, missing
business facts (hours, prices, phone numbers, claims), security-sensitive choices, anything outward-facing, and
accepting a check that could not pass. Routine fixes and re-tests happen without asking.

## Writing tickets so the agents do the right thing
WEB has no Acceptance Criteria field, so put them in the description:

```
<what and why, 1-3 sentences>

Acceptance criteria
- Header shows the store categories (Trgovine, Ugostiteljstvo, …) as links instead of the "Naše poslovnice" dropdown
- Works at 390 px wide without horizontal scrolling
- Keyboard: every category link is reachable with Tab and has a visible focus ring

Out of scope: footer, store pages' hero
Content/source: (where facts come from, if new copy is needed)
Design: (link to the approved design, if any)
```
No criteria in the ticket → the analyst proposes some, clearly marked, and asks you to confirm them before
anything is built. Linked issues (blocks / is blocked by / clones) are used to order multi-ticket work.

## After a run: what to look at
Everything for a ticket lives in `.jira-work/<KEY>/` (local only, git-ignored):

| File | What it is |
|---|---|
| `qa-report.md` | The consolidated report, generated by `wf.py report`: verdict, preview command, changed files, ACs, gates, defects, risks, usage |
| `handoff.md` | The delivery verifier's independent judgement (the tables are in qa-report.md) |
| `traceability.md` | Acceptance criterion → test cases → results, defects, gates |
| `spec.md`, `plan.md`, `design.md`, `` | Requirements + assessment, chosen agents/skills/models, design and copy specs |
| `reports/NN-<agent>.md/.json` | Each agent's full report and structured result |
| `evidence/` | Screenshots, test scripts, smoke results |
| `state.json` | Machine state (stage, tasks, defects, decisions, gates, history) |
| `.jira-work/guard-log.jsonl` | Every external/destructive action the guard stopped or asked about (all tickets) |
| `.jira-work/decisions.md` | Your past decisions, reused for later tickets instead of asking again |

Preview: `python3 -m http.server 8642 --bind 127.0.0.1` in the project folder, then open
http://127.0.0.1:8642/ (the site also opens straight from disk).

## Usage and cost
- `/jira-work status --usage`, or `python3 .claude/skills/jira-work/scripts/usage.py --ticket WEB-25`: tokens per
  agent and model, read from the local Claude Code transcripts (measured), with cost and 5-hour-window share
  (**estimates**: list prices from `pricing` in `project.json`, and one calibration sample of about $0.40 per 1% of
  the window). Your real plan usage is in claude.ai under Settings → Usage; it is not visible to the scripts here.
- Per ticket, the orchestrator checks the estimates before each agent call (`resources` in `project.json`):
  **WARN** at 35% of the window, 15 agent calls, 4 fix rounds or 2 h; **APPROVAL REQUIRED** (it stops and asks you)
  at 70%, 30 calls, 8 fix rounds or 5 h. Required checks are never skipped to save cost; it asks you instead.
- Reference: the WEB-25 dry run (analysis + one design task, no build) cost about $7.26, about 18% of a window.
- Tests and validation of the system itself use mocked agent reports and make no model calls. Live test runs on
  synthetic tickets happen only when you approve them.

## Approving commit, deploy or Jira updates (separately, after your review)
Say exactly what you want, for example "commit WEB-25", "push to main", "add the QA summary as a comment on
WEB-25", "move WEB-25 to Done". Claude still shows a permission prompt for each push, deploy or Jira write; that
prompt is your final confirmation. Approval covers that action once.

## Safety net (what is enforced, not just instructed)
`.claude/hooks/guard.py` runs before every Bash, file-write, Artifact and MCP tool call, in the main session and
in every agent:
- **Asks you first:** git push, merge, rebase, reset --hard, clean -f, branch -D, checkout/restore that discards
  changes, stash drop; GitHub CLI writes; Vercel/Netlify/other deploys; package publish; remote copies; curl
  writes to non-local hosts; any MCP write (Jira/Confluence comment, edit, transition, create; Canva; Docs; …).
- **Blocks:** agents committing or touching git history; read-only agents (everyone except the developer) writing
  outside `.jira-work/`.
- In a non-interactive run (`claude -p`) or a background agent, an "ask" cannot be answered, so it is blocked.
- `.claude/settings.json` also holds "ask" rules for git push and Jira writes, and "allow" rules for Jira reads and
  the workflow scripts (so routine work does not prompt).
Limits: it matches commands as text (a quoted "git push" inside another command also triggers a prompt), and a
custom script could still reach the network; agents are instructed not to, and the verifier checks the log.

## Where things are (reusable vs project-specific)
| Reusable in any project (no Novalis in them) | Project-specific (Novalis) |
|---|---|
| `.claude/agents/*.md` - the 9 specialists | `.claude/workflow/project.json` - Jira site/keys, stack, commands, design sources, languages, quality targets, budgets, deploy target |
| `.claude/skills/jira-work/` - orchestrator, references, `scripts/wf.py` (state), `scripts/usage.py` (usage), tests | `.claude/workflow/smoke.js` - regression smoke test for these 8 pages |
| `.claude/skills/jira-agent-protocol/` - shared rules + report contract | `CLAUDE.md`, `BRAND.md` - project rules and brand |
| `.claude/hooks/guard.py` + the `hooks` block in `.claude/settings.json` | Jira tool names in `settings.json` and in `jira-requirements-analyst.md` (`tools:`) |

**Use it in another project:** copy `.claude/agents/`, `.claude/skills/jira-work/`,
`.claude/skills/jira-agent-protocol/`, `.claude/hooks/guard.py` and the `hooks` block of `.claude/settings.json`;
write that project's `.claude/workflow/project.json` (copy this one and change every value) and, if useful, a
smoke test. If the Jira MCP server has a different name there, change the `mcp__plugin_design_atlassian__…` names in
`jira-requirements-analyst.md` and `settings.json`. Installing the reusable part globally (`~/.claude/agents`,
`~/.claude/skills`) works too, but project files override global ones of the same name; ask Claude to do it if you
want that.

## Changing the system
- **Warn/approval thresholds** (estimated window %, agent calls, fix rounds, time; `null` turns one off): `resources`
  in `project.json`; prices per model: `pricing`; the window calibration: `resources.subscription`.
  For one ticket, "allow WEB-25 twice the usual" raises its approval thresholds (`resourceAllowance`).
- **Models:** agents inherit your session's model; the orchestrator picks a cheaper one per call only where
  `reference/assessment.md` allows it.
- **An agent's job, tools, model or turn limit:** edit its file in `.claude/agents/` (frontmatter `tools`,
  `model`, `maxTurns`; body = instructions). Restart Claude Code (or open `/agents`) to load changes.
- **Add an agent:** new `.claude/agents/<name>.md` with `name`, `description`, `tools`, `skills: [jira-agent-protocol]`;
  add it to the tables in `.claude/skills/jira-work/reference/agents-and-skills.md` and, if it is read-only,
  to `READ_ONLY_AGENTS` in `guard.py` (and a test in `tests/test_guard.py`).
- **Add a skill to an agent:** install the skill, check its SKILL.md for side effects (asks questions, saves to
  `docs/`, commits, generates images), then name it in the agent's "Skills" section and in the skill map. Use
  "checklist only" for skills whose workflow conflicts with the rules.
- **Quality gates / approval rules:** `reference/quality-gates.md`, `reference/approval-and-safety.md`.

## Troubleshooting
| Symptom | Fix |
|---|---|
| `/jira-work` unknown, or agents missing | Restart Claude Code in this folder; check `.claude/skills/jira-work/SKILL.md` and `.claude/agents/` exist |
| Jira calls fail | `/mcp` → the Atlassian server (plugin "design") must be connected; re-authorise on claude.ai if needed |
| Prompts for every `wf.py`/Jira read | Project allow rules are ignored until the folder is trusted: run `claude` once in a terminal in this folder and accept the trust prompt |
| "EXISTS … stage=…" on start | The ticket already has state; use `continue <KEY>` (or ask to restart it, which archives the old state) |
| "NOT READY" with reasons | Read the listed reasons in `qa-report.md`; most need a decision from you or another fix round |
| "NO PROGRESS", "NO CHANGE" or "APPROVAL REQUIRED" | A fix did not change the failure, or the ticket reached an approval threshold; the orchestrator stops and asks you (more allowance, change scope, accept as known issue) |
| A check shows "stale" | Files changed after that check passed; it is re-run before the ticket can be ready |
| Smoke test can't start Chrome | macOS 13 needs system Chrome (`channel: 'chrome'`); `source ~/.nvm/nvm.sh` for node |
| Interrupted mid-run | `continue <KEY>`: it compares state with git and Jira and redoes only unfinished tasks (agents do not survive a closed session) |
| Guard blocked something legitimate | The reason is in the message and `.jira-work/guard-log.jsonl`; approve the prompt, or adjust the pattern in `guard.py` + its test |
